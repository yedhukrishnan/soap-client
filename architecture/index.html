How it's built.
Rust inside, web on top.

A tour of the architecture, the technology choices and the reasons behind them. Written for anyone who knows software but not necessarily Rust.

// overview

Import a WSDL, get a request for every operation, send it, check the response.

A WSDL is the XML file that describes a SOAP service. SOAP Client reads it, along with every schema it imports, and writes a ready-to-edit sample request for each operation. You fill in values, press Send, and the response comes back with automatic checks: status code, XPath, no SOAP Fault, response time. Around that loop sit environments and {{variables}}, HTTP Basic and WS-Security, secrets in the system keychain, autosave and shareable project files.

// three layers in one app

The app is one native program with a web page inside it. The page draws the interface; Rust does everything that touches the network, the disk or the keychain. They talk over Tauri's IPC bridge, which works like calling a local API. The Rust half is split again: a thin shell that knows about Tauri, and a core library that knows nothing about any UI.

The one rule that shapes everything: the project lives in the UI, the secrets live in Rust. The UI holds and edits the project as plain data and asks Rust to do work on it. Secret values go into the keychain through Rust and never come back out to the page.

Why split Rust into a core and a shell?testability

A Cargo workspace holds two crates. soap-core has no UI or Tauri dependency, so cargo test runs every WSDL, HTTP and assertion test without opening a window. src-tauri is the app; its commands are mostly one-liners into the core. A different front end, such as a command-line tool, could reuse the core unchanged.

Why Tauri and not Electron?size and security

Electron ships Chromium and Node.js in every app. Tauri uses the system webview and a Rust backend, so downloads are small and memory use is low. The page has no direct file or network access: it can only call the commands registered in lib.rs and the permissions in capabilities/default.json. The cost is that webviews differ by OS (WebKit on macOS, WebKitGTK on Linux), so Linux packages are install-tested on clean systems.

Why does the interface own the project?simplicity

Editing is constant, and keeping that state in Rust would mean an IPC round trip per keystroke. Instead the UI holds the project and sends a snapshot to save 700 ms after the last change. Rust keeps only three pieces of state: requests it may need to cancel, the secret store, and a lock for update preferences.

Why one keychain item per project?fewer prompts

Every keychain read can make macOS ask for permission or Touch ID. So all of a project's secrets share one JSON "vault" item, read once and kept in memory until unused for 15 minutes. "Is this secret set?" is answered from a file that lists only key names, which never prompts.

// how things flow

Importing a WSDL

  1. ui

    The import dialog takes a URL or file and calls api.importWsdl(source).

  2. shell

    import_wsdl hands it to soap_core::project::import_wsdl.

  3. core

    wsdl/loader.rs fetches it and follows every wsdl:import, xsd:import, include and redefine, resolving relative paths against the final URL after redirects. Up to 250 documents of 20 MB each.

  4. core

    wsdl/parser.rs indexes all schema types, then flattens bindings, port types and services into interfaces with operations and endpoints.

  5. core

    xsd/sample.rs writes a sample envelope for each operation, reusing the WSDL author's prefixes and guarding against recursive types.

  6. ui

    The result, including the text of every imported document, is stored in the project, so it works offline afterwards.

Sending a request

  1. ui

    Send collects the request and the active environment's variables. Secrets are passed as a keychain key, not a value.

  2. shell

    send_request finds which {{names}} are used and reads only those secrets.

  3. core

    vars::resolve_spec substitutes them. Any undefined variable stops the send and is named, so nothing half-filled goes out.

  4. core

    http::prepare adds SOAP 1.1 or 1.2 headers and Basic auth or WS-Security; your own headers win.

  5. core

    http::send posts it. Cancel races it with tokio::select!.

  6. core

    The response returns with timing, size, a pretty-printed body and a copy of the request with secrets shown as ••••••.

  7. ui

    run_assertions checks it and the results appear beside the response.

// what it defends against

Keeping secrets secret

  • Secret values are never in project files, the session file or the UI. The UI can set, delete and ask "is it set?", nothing more.
  • Wherever a sent request or an error is shown, secret values and their XML-escaped forms become ••••••.
  • Signed macOS builds require Touch ID or the Mac password to read secrets, and lock again after 15 idle minutes.
  • A project file that isn't known to be yours must ask before it can use stored secrets.
  • With no keyring available, secrets are kept in memory only, until quit.

Not trusting the network or the page

  • SOAP requests follow redirects only to the same scheme, host and port, so headers and bodies can't leak elsewhere.
  • WSDL downloads may redirect, but never from https to http.
  • A WSDL from the web can't import file:// paths, and every import must be a schema or WSDL.
  • No Referer header, since URLs can hold secret variables.
  • Size limits on documents, import count and responses.
  • Save and open accept only absolute .json paths.
  • A strict Content Security Policy: the page loads only its own scripts and talks only to the IPC bridge.

Releases

  • Linux: GitHub Actions builds .deb for amd64 and arm64 in an Ubuntu 22.04 container on every version tag, repackages it for Arch, and install-tests each on a clean system.

  • Updates: the app reads latest.json from this site once a day. Nothing about you is sent.

Crates, Cargo and the workspace

A crate is a package. Cargo is Rust's npm: Cargo.toml is the package.json, crates.io the registry. A workspace groups crates that build together.

# Cargo.toml
[workspace]
members = ["crates/soap-core", "src-tauri"]

# src-tauri/Cargo.toml
soap-core = { path = "../crates/soap-core" }

Structs and derive

A struct is like a TypeScript interface that holds data. #[derive(Serialize, Deserialize)] generates JSON conversion; rename_all = "camelCase" turns soap_action into soapAction to match the TypeScript side.

#[derive(Serialize, Deserialize)]
#[serde(rename_all = "camelCase")]
pub struct RequestSpec {
    pub endpoint: String,
    pub soap_version: SoapVersion,
    #[serde(default)]
    pub soap_action: Option<String>,
    pub body: String,
}

Enums carry data

Like TypeScript discriminated unions: each variant has its own fields. match handles every variant, and the compiler errors if one is missing.

#[serde(tag = "kind")]
pub enum Auth {
    None,
    Basic { username: String, password: String },
    WsSecurity(WsSecurity),
}

match &spec.auth {
    Auth::None => {}
    Auth::Basic { username, password } => { /* header */ }
    Auth::WsSecurity(sec) => body = apply_ws_security(&body, sec)?,
}

Option and Result

No null: a value that may be missing is Option<T>, either Some(x) or None. No exceptions: a fallible function returns Result<T, E>, either Ok or Err. A trailing ? means "if this failed, return the error now".

pub fn save_project(path: PathBuf, project: Project)
    -> Result<(), String>
{
    let path = project_path(path)?;   // bail unless .json
    project::save(&project, &path)
        .map_err(|e| e.to_string())
}

Ownership and &

Every value has one owner and is freed when the owner goes away; that's how Rust manages memory without a garbage collector. &x lends a value, &mut x lends it for changing, .clone() copies it. &str is borrowed text, String is owned text.

// borrows spec, doesn't take it
pub fn prepare(spec: &RequestSpec) -> Result<PreparedRequest> {
    let mut body = spec.body.clone();  // own copy to edit
    ...
}

async and tokio

async and .await work as in JavaScript, but Rust needs a runtime to run them: tokio. tokio::select! waits on several futures and takes the first to finish. That's the whole Cancel feature.

let result = tokio::select! {
    r = soap_core::http::send(&spec, &masked) => r,
    _ = rx => Err("Request cancelled".to_string()),
};

Tauri commands

#[tauri::command] makes a function callable from JavaScript, with arguments decoded from JSON. State<'_, T> arguments are injected by Tauri. Each command is also listed in generate_handler!.

// Rust
#[tauri::command]
pub fn format_xml(xml: String) -> Option<String> {
    soap_core::xml_fmt::pretty_print(&xml)
}

// TypeScript, ui/src/lib/api.ts

Small things you'll see

pub is public. mod x; includes x.rs. use is import. #[cfg(target_os = "macos")] compiles code only on macOS. Mutex guards shared data across threads. |x| … is a closure. 'a is a lifetime, telling the compiler how long a borrow lasts; you can mostly skip it when reading.

#[cfg(target_os = "macos")]

A reading order

  1. ui/src/lib/types.ts: every data shape in one file.

  2. ui/src/lib/api.ts: everything the UI can ask Rust to do.

  3. src-tauri/src/commands.rs: what each of those does, in about 190 lines.

  4. crates/soap-core/src/http.rs: the heart of sending a request.

  5. ui/src/lib/state.svelte.ts: how the UI holds and changes the project.

Example: a new assertion type

  1. core

    Add a variant to Check in assertions.rs.

  2. core

    Handle it in evaluate; the compiler points at the match until you do.

  3. core

    Add a test beside it and run cargo test.

  4. ui

    Add the same shape to Check in types.ts.

  5. ui

    Add its fields to AssertionsEditor.svelte and run npm run check.

No new command is needed, because run_assertions passes the whole list through. New backend work means a command in commands.rs, registered in lib.rs, with a wrapper in api.ts.

// glossary

SOAP
An XML protocol for calling remote services. Each message is an Envelope with an optional Header and a Body. Versions 1.1 and 1.2 differ mainly in namespace and content type.
WSDL
An XML file listing a service's operations, message formats, bindings and addresses. SOAP Client supports WSDL 1.1.
XSD
XML Schema: defines what elements and types look like. WSDLs embed or import schemas.
Binding / port
A binding ties operations to SOAP specifics; a port gives it an address. The app shows one interface per binding.
Document / RPC
Two body layouts: one schema element, or a wrapper named after the operation.
SOAP Fault
The standard error element a service returns when a call fails.
WS-Security
An OASIS standard for credentials in the SOAP Header; here, UsernameToken with text or digest passwords.
XPath
A query language for picking parts of an XML document.
IPC
How the page inside the app calls Rust and receives events.
Webview
A browser engine embedded in a window, without the browser around it.
CSP
Content Security Policy: what a page may load or connect to.
Notarization
Apple scanning a signed app so macOS opens it without a warning.
Secret Service
The freedesktop.org API that Linux keyrings implement.
